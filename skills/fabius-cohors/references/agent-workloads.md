# Fabius Castra — run an agent as a workload

Loaded on demand by `fabius-cohors`. *Castra* is the legion's camp, built to the same plan every night: this is that plan for the layer that HOSTS an agent — its unit, its lifecycle, what the orchestrator may believe about it and what proves each claim. The container is [`local-agent-runtime.md`](local-agent-runtime.md) §13; checkpoints and LOST are [`agent-evaluation-and-durability.md`](agent-evaluation-and-durability.md) §2; the coordinator that composes units is [`agent-patterns.md`](agent-patterns.md).

## 1 · The unit is shape-blind

A runtime hosts agents; it does not describe them. Its primitive is one sealed work unit — an isolation boundary, an instruction, a set of states — and the unit is the same object whether it carries the whole job or one leaf beneath a coordinator. What an agent intends next, what it retries, whom it delegates to and who asked for it are the coordinator's facts, kept in the caller-owned coordination layer (`agent-patterns.md`) and never in the unit's host. Every step list, retry counter or parent link the runtime types as a first-class object is a bet on one agent's structure that the next agent must work around. How deep units nest is orchestration policy (the depth-1 spawn cap), not something the unit models; containment and caps stay per unit, as §13 of the runtime guide fixes them. The test: the agent can finish in one unit or a thousand identical ones and the runtime cannot tell the difference.

## 2 · Born held — four lifecycle verbs

Creation and start are separate verbs. A unit is born **held**: provisioning creates it, a distinct start admits it to run, so a quota, a gate or a human sits between the two and is enforced by the runner — never by the agent's promise to pause (doctrine §9). **Pause** keeps the unit and its checkpoint and reports not-ready with a named reason; **resume** re-admits it; **retire** ends it (§4). Held and paused are statuses beside running · completed · failed · LOST — never a false running or a false failed. A human-in-the-loop gate is *hold at creation, start on approval*, not spawn-and-hope; kill-and-restart is the last fallback (durability §2, M4), never the way to wait. Paused is asserted from the host's reply, not from having issued the call — writing "paused" when the checkpoint call returned an error records intent as fact. Prove pause by resuming: the unit continues on a fresh process tree with its files intact (§6 says what a fresh process tree destroys if you let it).

## 3 · The brief is frozen; change arrives as a successor

A dispatched brief is immutable the moment its worker starts. The coordinator never edits or messages a running worker to change its task — a mid-run correction arrives as a rival instruction, and the worker's claim to one contract dies with it. The plan still evolves (doctrine R6): stop the affected worker, record its last observed status against the brief it was given, dispatch a **successor** under a new id. A unit's identity is its launch brief, not its status — status writes to the same row, a changed brief opens a new one, so the task table reads as history, never as a rewrite. Name any launch snapshot from the brief alone with observed status stripped first: status churn mints nothing, and every real change to what runs shows as a new snapshot. A successor with a changed brief starts fresh or from a summary, never by RESUME_FROM inheritance, whose same-instructions constraint it fails by definition (`agent-patterns.md`, *Durability*).

## 4 · Teardown in a fixed order, with durable intent

A unit that owns real resources — a container, a process, a snapshot, a key — is retired in one order: mark its record **retiring** in the store it lives in, release everything it owns, then remove the record. The mark is durable intent: a crash mid-teardown leaves a record that says retiring — never a false running, never a live sandbox with no record — and the next start finishes any teardown still marked. Retirement is synchronous: the caller returns only after release, and gets the release failure when there is one; a record still marked retiring is the visible debt. Every owned resource counts, not only the primary one: a secondary release that fails, logs and is swallowed is an orphan with a log line — hold the record or report the leak by name. A resource already gone counts as released.

## 5 · Alive is not ready — and ready has three outcomes behind it

A runtime exposes two signals, never one: **alive** (the process answers) and **ready** (the environment it promised is in place). The orchestrator dispatches on ready alone; an alive worker over a half-built workspace is the entry-side twin of a loop with no exit gate. Ready is the conjunction of every declared preparation step's *verified* outcome — the checkout that exists, the tool configuration actually written, the bootstrap that returned — never the absence of a returned error. Each declared step has three observable outcomes: **met**, **failed**, **not attempted** (script absent, credential missing, prerequisite unmet), and ready may only mean *met, for every step*. A best-effort step that logs its failure and returns success has lied to the caller; a step skipped with a log line and a computed flag nobody reads is indistinguishable from one that succeeded — that is the failure, whatever the log level. What the docs say readiness guarantees must be exactly the set of steps the code verifies; a promised step no code performs is a false guarantee the orchestrator will act on.

Prove it by forcing one step to fail and one to be skipped, and asserting the orchestrator never dispatches in either case, with the step named in the not-ready reason. A comment promising "never ready on failure" is not evidence; readiness that cannot say *not attempted* is not evidence either ([`codebase-and-proof.md`](../../fabius-disciplina/references/codebase-and-proof.md) §4).

## 6 · Preparation is idempotent by evidence, proven on the second boot

One-time preparation — whatever fills the tree, mounts it, writes its declared content or bootstraps its toolchain — is a side effect, and the durability law applies: resume must not re-run it. Its completion marker lives on the **same durable surface as the state it protects** — the volume that survives checkpoint and restore — never on the container's own disk, which a resume discards. A marker on the ephemeral disk vanishes exactly when it is needed, and the restored workspace then meets a forced re-checkout: uncommitted edits discarded, declared files rewritten, the bootstrap re-run behind a readiness gate that reports success — the partial-batch law's duplicate side effect wearing a `git` prefix. Write the marker only after every step that must succeed has succeeded; a step you made best-effort records its own outcome beside it (§5's three outcomes), so an unfinished bootstrap is visible and resumable instead of silently unrepeatable. Before touching a workspace, setup reads what is there: a checkout carrying uncommitted work is an agent's state, and a forced re-fetch into it is data loss.

The acceptance probe is the **second boot after a checkpoint and restore**, not the first: pause, resume into a fresh container, assert setup stepped aside and the tree is byte-identical. First-boot idempotence proves nothing about the restart the marker guards against; restore-then-boot is the surface for any resume claim (disciplina's *prove at the surface*).

## 7 · Two privilege contexts: prepare, then run

Building the workspace and running the agent are two privilege contexts, never one. Whatever fills the tree from outside — the fetch credential, the registry key, a model key only the bootstrap needs, the egress fetching needs — runs first and ends before the agent's first instruction; all it leaves behind is the filled directory. The run context starts with none of those secrets, only the single provider credential it needs (the runtime guide's §13 invariant) and the job's minimum egress, so nothing the agent writes or pulls can find the token that built its tree. Need is measured per phase, not per job: at the hand-off the supervisor rebuilds the child's environment from an explicit allow-list, and a credential the run phase does not consume is *absent*, not merely unused — appending to the parent's environment is inheritance wearing a longer list. The stronger form is praesidium's: keep the secret out of the sandbox and let the proxy attach it on egress ([`hardening-guides.md`](../../fabius-praesidium/references/hardening-guides.md) §9); phase-scoping is the floor when the key must be inside.

Prove it from inside the running worker: dump its environment, mounts and reachable hosts at the task boundary. The supervisor's intent, its policy file and its docs are claims (durability §4: a policy edit is not proof). A secret the docs list as a general variable with no phase is an undeclared scope to settle first, not a proven leak.

## 8 · Supervise the group, and decide who outlives whom

Start the agent in its own process group and stop it by signalling the **group**, never the pid: a courteous signal, a timed wait, then force — so the tool servers, dev servers and watchers it spawned go down with it, and a shell tool's timeout obeys the same law. A group is a fence, not a wall: a helper that starts its own session steps outside it, so prove teardown by killing the supervisor and listing what survives, not by reading the code. The reverse is a decision, not an accident. A throwaway job container (runtime guide §13) ends with the job; a sandbox that must stay inspectable or resumable keeps the supervisor up after the agent exits, records the exit as an event (§9), and ends on its own stop signal — never the agent's. Verify both directions by killing: kill the parent and the agent dies (runtime guide §2); stop the agent and nothing it spawned survives.

## 9 · The outcome record, never the exit code

An exit code is a fact the supervisor sees; assume the orchestrator never does. Across a sandbox boundary the layer above cannot observe process state, and a supervisor that stays up (§8) has no exit to forward. A supervised run therefore ends by **writing its outcome record** — the terminal verdict with pointers to its evidence — where the orchestrator actually reads: the shared workspace, the record store, or a status endpoint it polls. A return value or a log line is not that place. The orchestrator decides from that record and never infers completion from a container still up or a log gone quiet; no record past the deadline is **LOST** — not still-running, not success (durability §2 owns the status set; the record fills it). Before shipping the pair, prove that the terminal state the watcher waits on is one some component really writes: a watcher polling for a status nothing ever sets waits forever after a clean exit. The deadline-forced final turn in `agent-patterns.md` (*Terminate with a report*) is the agent's half; this record is the harness's.

## 10 · Declared files travel with the environment

An agent's standing rules, project guidelines and small config are declared content in the environment spec, written into the sandbox before the first command — versioned with the environment, rewritten on every fresh boot, never carried as prompt text. Two consequences. A declared file is a *write*: an absolute path lands anywhere in the sandbox root, so it is reviewed as code, not configuration (praesidium's [`supply-chain-and-ai-artifacts.md`](../../fabius-praesidium/references/supply-chain-and-ai-artifacts.md) owns that review). And it is a preparation step under §5 and §6: it has an outcome, and a resume must not rewrite it over an agent's edits.

## 11 · The runner contract is a seam

The launch command is the host's, never the unit's: the host always starts one supervisor of its own choosing, and the unit's command reaches that supervisor only inside the spec it is handed. The supervisor is fed two serialized documents — the environment declaration and the unit's own spec — and probes one readiness path that the sandbox host and the orchestrator both read. Whatever image is named, the host holds it to the same contract and asks nothing else of it. That contract makes the agent framework swappable — a replacement ranges from a few extra tools baked into the image to a supervisor written from nothing — without the orchestrator noticing. Each distinct pairing of image and environment gets one snapshot of its own, keyed by a digest of both (§3). A replacement supervisor is accepted when it reads both documents from where the orchestrator places them, exposes only the surfaces the orchestrator polls, and passes the checklist at the end of this file.

## 12 · Waiting is a checkpoint and a wake condition, never a poll

A waiting agent is not a running agent. At a human gate, a webhook or a long poll, the run declares the wait, writes its checkpoint and yields the slot — the wait is a stored row with a wake condition (the event, or a next-check time) in the job ledger (`agent-patterns.md`, *The standing-job agent*), never a live process sleeping inside the loop. Waking is a resume from that checkpoint under the repair-the-partial-batch law: the event arrives as data, state is read back before acting. Declaring the wait is the agent's job; inferring idleness from resource silence is a host's fallback, not a design.

## 13 · The harness keeps the record; the agent never narrates its own run

Observe agents from the layer that runs them, never from inside them. The harness records each change of run state as it happens and, inside every state, each exchange with the model and each tool's reply — for every agent it hosts, from the moment of dispatch, with nothing to add and nothing to switch off. That record, not the agent's returned summary, is what the eval suite scores (durability §1) and what an incident timeline is rebuilt from; an account an agent gives of itself is a claim to check against the record, never the record. The per-model-call history that already makes a run resumable (durability §2) *is* this record — keep one, not two. Read it as evidence about the run, never as instructions to the next one (the untrusted-content rule, [`fabius-praesidium`](../../fabius-praesidium/SKILL.md) §3).

## The checklist

- [ ] One unit shape, four verbs, no plan/retry/ancestry field; nesting is the coordinator's policy.
- [ ] Born held; a gate is hold-then-start; paused is proven by a resume.
- [ ] A brief never changes in flight; a change is a successor; snapshot names derive from the brief, status stripped.
- [ ] Retire = mark retiring → release everything owned → drop the record; the caller waits for it; a swallowed failure is a named leak.
- [ ] Alive and ready are two signals; a forced fail AND a forced skip both hold ready false, step named.
- [ ] Setup marker on the durable volume; the second boot after restore leaves the tree byte-identical.
- [ ] The run-phase environment, dumped from inside, holds no fetch or registry credential and only the declared egress.
- [ ] Stop signals the process group with a grace; killing the supervisor leaves no survivors; who outlives whom is written down.
- [ ] The outcome record lands where the orchestrator reads, and the terminal state it waits on is one that gets written.
- [ ] The supervisor is a fixed binary fed two serialized documents and probed on one readiness path; a replacement passes the same probes unchanged.
- [ ] Declared files are reviewed as writes; a wait is a ledger row, not a sleeping process; the harness record, not the agent's summary, feeds eval and incidents.
